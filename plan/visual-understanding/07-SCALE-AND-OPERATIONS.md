# 07 — Phase VU8: very high scale

"Very high scale" here means a 10-hour library, a 1,000-asset project, a machine with 8 GB,
and a user who imports while a render runs. Every property below is tested, not asserted.

## 8.1 Cost model

| Work                     | Complexity                          | When                                       |
| ------------------------ | ----------------------------------- | ------------------------------------------ |
| Tier 0                   | O(footage seconds) at 2 fps 160 px  | import, background                         |
| Tier 1                   | O(shots)                            | import, background, after tier 0 per asset |
| Tier 2                   | O(shots), slow                      | import, background, lowest priority        |
| Entity clustering        | O(new faces × clusters) incremental | after each tier 1 slice                    |
| Duplicate detection      | O(shots) with a 64-bit multi-index  | after each tier 0 slice                    |
| Ledger snapshot to a run | O(shots of timeline assets), paged  | run start, asset add                       |
| Picture slice            | O(clips) memoized per revision      | per apply                                  |
| Prompt                   | O(clips shown) + 600 tokens         | per turn                                   |
| Verification             | ≤ 4 pairs, ≤ 2 vision pairs         | per picture apply                          |

Nothing is O(decisions × footage). That is the whole scaling argument.

## 8.2 Priority and scheduling `[ ]`

One ledger loop per project (the enroller already enforces this). Worklist order:

1. assets referenced by the timeline, in timeline order;
2. assets in the bin, most recently imported first;
3. everything else.

Tiers run per asset in order 0 → 1 → 2, but the loop advances tier 0 across the whole
worklist before starting tier 2 anywhere, so the cheap facts exist for every asset before the
slow tier begins. A newly imported asset preempts the queue at tier 0.

## 8.3 Resource governor `[ ]`

In the sidecar, one governor with fixed rules:

- Tier 0 workers: `max(1, cores ÷ 4)`; tier 1: 1; tier 2: 1.
- Pause all tiers while a render, export, `get_frame` or `temporal-evidence` batch is in
  flight (the existing `_temporal_evidence_gate` is the model), resume after 2 s idle.
- Memory: tier 2 refuses to start when free memory < 2 × model resident size; records
  `skipped: low_memory` and retries on the next slice.
- Thermal/battery (macOS): on battery, tier 2 runs only when the app is focused-idle; setting
  in Settings → AI → Media intelligence, default on.

## 8.4 Resumability and idempotency `[ ]`

- The job payload is the worklist + cursor + tier flags (the existing pattern).
- Kill the sidecar mid-slice: on restart `sweep_interrupted_jobs_once` marks the job
  interrupted; the next slice resumes from the cursor; per-shot writes are transactional per
  asset per tier, so a partial asset re-runs its tier, never a half-written shot.
- Content-hash keys: re-import of identical bytes is a no-op; a re-encoded file re-runs.
- Tier version bumps null one column and re-queue that tier only.

## 8.5 Storage and eviction `[ ]`

- Ledger rows ~1.5 KB/shot; vectors 1.5 KB/shot fp16. A 10-hour library ≈ 25 MB. No
  eviction needed for the ledger.
- Keyframe JPEGs (`frames` table, `sidecars/`) are the only large derived artifact: bounded
  to 768 px today; cap per project at 2 GB with LRU eviction; a missing keyframe is
  regenerated on demand, never a failure.
- Deleting the brain rebuilds everything (ADR 0058).

## 8.7 Observability `[ ]`

- `log.action` on job start/slice/done per tier with counts and durations (never pixels or
  keys).
- Settings panel: per-tier coverage, current asset, ETA from measured rates, pause/resume.
- Agent: `coverage` fact in the digest; `describe_footage` says which tier its words came from.
